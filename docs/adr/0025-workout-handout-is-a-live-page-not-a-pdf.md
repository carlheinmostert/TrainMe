# Workout handout is a live interactive page at /h/, not a PDF

The free workout handout artifact is a **live, interactive web page** at `session.homefit.studio/h/{planId}` — rendered on demand from the live plan via the existing anon `get_plan_full` RPC, never materialised. It carries a soft claim CTA, a QR pointing back to `manage.homefit.studio/r/{referralCode}` so handout traffic that signs up attributes correctly to the practitioner, the same consent-gated three-treatment toggle the player has (Line · B&W · Original, locked segments where the client hasn't consented), a Print/Save-PDF button that's a single browser-native `window.print()` against a `@media print` stylesheet on the page itself (not a generator service, not html2canvas, not jsPDF), and a permanent "powered by homefit.studio" seal in the footer. Free — 0 credits — and the funnel artifact: the handout is the cheapest hand-off and the entry into the engagement loop. New `plan_artifacts.kind = 'handout'` widens the CHECK constraint introduced in [ADR 0022](0022-plan-artifacts-abstraction-before-reel.md) (was `CHECK (kind IN ('plan_url'))`); the row is computed on first request and the `output_url` stays `NULL` because there's nothing to store — the URL is computed from `plan_id`, the page is server-rendered or anon-RPC-fetched at each open. This **reverses the shipped behaviour** of the on-device multi-page PDF handout that the lobby export pipeline produces from `web-player/lobby.js` + `html2canvas.min.js` + `jspdf.umd.min.js` via the `is-exporting` snapshot class in `web-player/styles.css`, handed back to Flutter through the `share_file` payload on the `UnifiedPreview` scheme bridge (`app/lib/screens/unified_preview_screen.dart` and `app/lib/services/unified_preview_scheme_bridge.dart`). That pipeline has shipped since 2026-05-15 (the implementation of the predecessor spec [`docs/FREE_LOBBY_EXPORT.md`](../FREE_LOBBY_EXPORT.md), itself a partial supersede of the original PNG-first proposal). It is deprecated by this ADR. The export-only DOM rendering path, the html2canvas + jsPDF vendor bundles, the `is-exporting` / `lobby-export-page` CSS blocks, and the `share_file` / `share_image` payload handlers all schedule for deletion in the same wave that lands `/h/`. Reader-App compliance is preserved per [`feedback_ios_reader_app.md`](../../.claude/projects/-Users-chm-dev-TrainMe/memory/feedback_ios_reader_app.md) — the handout copy is purchase-neutral; the claim CTA reads as "save this workout to your phone", not "subscribe" or "upgrade".

## Considered Options

We considered **keeping the shipped on-device PDF handout** as the free artifact. Rejected because a PDF is dead — there is no mechanism for a soft claim CTA, no actionable QR, no live update when the practitioner edits the plan a day later, no per-page analytics signal, and no way for the post-claim consent flips (toggling B&W or Original on for a client who's already received the handout) to reach the already-distributed copy. The recipient holds a frozen artifact that can never be improved; the practitioner cannot reach them through it. A live page solves all of that at the cost of "PDF generation" complexity that turns out to be one `@media print` block on the live page itself — and the print fidelity is in fact better, because the browser composes against the live layout rather than against a screenshot taken at an arbitrary viewport size.

We considered a **hybrid: live page AS WELL AS the on-device PDF pipeline**, keeping both render targets so practitioners with intermittent connectivity can still hand over a PDF. Rejected because two render targets for the same conceptual artifact is the exact divergence the [`plan_artifacts`](0022-plan-artifacts-abstraction-before-reel.md) abstraction is designed to prevent. The R-10 parity tax that already exists on `web-player/styles.css` (the same stylesheet must read sensibly both as the live player chrome and as the snapshot source for the PDF generator) was already painful; doubling it with a third surface that has yet a third set of constraints (print + claim CTA + QR) compounds the cost and guarantees one of the three drifts.

We considered the **WhatsApp inline PNG image** as the primary free format — the original `FREE_LOBBY_EXPORT.md` proposal that renders the plan as a single unfurl-friendly image. Rejected for three reasons. First, a 10-exercise plan rendered to a single PNG is too small to read without tap-to-zoom, breaking the "renders inline beautifully" premise that motivated the format. Second, an image is *dead*: leads nowhere actionable, no claim path, no QR follow-through, no consent-gated treatment toggle. Third, the engagement loop wants a click — an impression alone doesn't convert. PNG is demoted to an optional later `poster` kind in `plan_artifacts` if the share-rate data justifies it; the link-unfurl quality of the new `/h/{planId}` page itself can be mitigated cheaply with a `@vercel/og` generated OG preview image as a fast-follow without re-introducing PNG as a primary artifact.

We considered a **higher consent bar on the printable view** — line-drawing only on print, even when the consumer has consented to B&W or Original. Rejected as a nanny move per locked decision #10 of the design doc: the consent matrix is the consent matrix regardless of render format. If the client has consented to the un-obscured original on the player, they have consented to it on the print. Layering a format-specific override would force a second consent UI (or worse, a silent override that the practitioner couldn't reason about) for no privacy gain.

The trade-offs we accept by going live-page-only are narrow and surfaced explicitly. We lose offline / no-signal sharing — the on-device PDF could be saved and AirDropped without ever touching the network; the live page requires connectivity at open time. The loss is narrow because publish has always been online-only and the practitioner typically hands the link over on the same network they captured on; the recipient's connectivity is no worse than what the player itself requires. The shipped `is-exporting` CSS, `html2canvas` + `jsPDF` vendor bundles, and the `share_file` bridge handler become dead code; rather than leaving them as a parallel path that bit-rots, Carl owns scheduling their deletion in the same PR that ships `/h/`. Print quality depends on the recipient's browser print stylesheet support — generally fine on Safari, Chrome, Firefox, and Edge, possibly weird on legacy browsers; the print stylesheet hides the claim chip and treatment toggle (uninteractable on paper) and uses a tested fixed layout, but a tail of low-end devices will print imperfectly. That tail is acceptable as long as the live-page reading experience itself remains the primary mode.
