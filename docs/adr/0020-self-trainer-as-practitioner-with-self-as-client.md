# Self-trainer is a Practitioner whose only Client is themselves

The self-trainer persona (gym-goer, influencer, anyone using Safe Mode to film themselves) is modelled as a Practitioner whose personal practice contains exactly one Client, with `clients.user_id = auth.uid()`, rather than as a new identity type with its own data model. The Self-client is created lazily on Public profile save (the moment the user uploads a reference selfie and opts into face-verification), lives only in the user's personal practice, and is hidden from the Practice mode Clients tab — addressed only via the My Workouts surface. Plans owned by a Self-client are credit-exempt at Publish time when every exercise passes on-device MobileFaceNet self-verification against the registered selfie embedding. The credit-exemption decision happens inside the existing `consume_credit` RPC at publish time; there is no `plans.kind`, no `is_self_capture` discriminator, no parallel publish flow. A user who later adds a non-self Client becomes a working practitioner without any identity migration — the same `auth.users` row, the same `practice_members` row, just with more Clients in the list.

## Considered Options

We considered a separate **consumer identity** (no `practice_members` row; new `consumer_profiles` table; received plans only) as the original frame of [`docs/CLIENT_WORKOUTS_AND_CLASSES.md`](../CLIENT_WORKOUTS_AND_CLASSES.md). Rejected because the self-trainer persona genuinely creates content (Safe Mode self-captures with the line-drawing pipeline) — a consumer-only identity would have required bolting capture capability onto a model designed to be receive-only, doubling the surface area for no benefit. We also considered a **new third identity** (`self_trainer` role alongside practitioner/consumer with its own dedicated workouts table) — rejected because the schema overlap with Practitioner/Client/Plan/Exercise was near-total; new tables would have duplicated the entire existing CPE hierarchy. The chosen approach reuses every existing primitive — `practices`, `clients`, `plans`, `exercises`, `practice_members`, `credit_ledger`, the conversion pipeline, the Studio editor, the publish flow, the web player — and adds exactly two columns (`clients.user_id` + `practitioners.face_embedding`) plus a partial unique index. The trade-off is that "Self-client" is a slightly unusual concept (a Client who is also the User) but is bounded to the personal practice and never visible to users in that framing; they see "My Workouts" and never see themselves listed as a Client of themselves.
