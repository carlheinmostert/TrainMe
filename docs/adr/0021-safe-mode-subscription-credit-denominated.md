# Safe Mode subscription is credit-denominated, not Apple IAP

The Safe Mode subscription that unlocks capture inside enforcing geofences is priced in credits (4 credits / month = R100 at the locked R25/credit rate) and debited from the same `credit_ledger` that already powers per-publish credit consumption. New ledger `kind = 'safe_mode_month'`. First subscription includes a one-time 3-day free trial (no debit until day 4; 33 days total for the cost of 30). Renewal is manual — push notification at day 25, re-up via Settings → Subscription; no auto-debit in v1. Subscribed via `manage.homefit.studio` (Reader-App pattern preserved: no in-app prices or Subscribe buttons in the mobile app). Subscription lapse only gates *future* in-premises captures; existing captures and already-published Plan URLs stay accessible forever ("honor what you sold").

## Considered Options

We considered **Apple IAP via StoreKit 2** (the standard pattern for an in-app feature unlock). Rejected because: (a) it would require StoreKit integration, server-side receipt verification, a new `user_subscriptions` table, recurring-billing webhook handling, and Apple lapse semantics — real engineering that risks blocking the self-trainer wave from shipping; (b) Apple takes 15-30% of subscription revenue, meaningfully reducing the per-subscriber margin on what is a high-volume / low-price SKU; (c) most importantly, it would **silo the new revenue stream from the existing referral-rebate loop**. The 5% lifetime rebate ([`supabase/archive/schema_milestone_m_credit_model.sql`](../../supabase/archive/schema_milestone_m_credit_model.sql)) accrues rebates in credits — practitioner referrers earn credits they spend on publishes. With Safe Mode in credits, self-trainer referees burning credits on subscriptions feed the same flywheel: gym people refer gym people, both groups burn credits on Safe Mode access, the referrer earns rebates that they themselves spend on Safe Mode access. The previously-inert referral mechanic for the consumer side of the business (consumers don't publish, so they wouldn't earn rebates from referrers via the credit channel) now has a real burn surface and the loop spins. We also considered **deferring the subscription gating entirely** — ship self-trainer with Safe Mode temporarily free, build IAP as a focused follow-up wave. Rejected once the credit-denominated path emerged because the credit model lets us ship the paywall in v1 without any of the Apple IAP cost. The Reader-App pattern ([`feedback_ios_reader_app.md`](../../../.claude/projects/-Users-chm-dev-TrainMe/memory/feedback_ios_reader_app.md)) extends naturally — credits are purchased on the web portal; Safe Mode access is a debit against an already-purchased credit balance, identical to the existing publish-credit pattern. The trade-off is that subscription state is materialised as a query against `credit_ledger` (`is_in_active_safe_mode_sub(user_id)` checks for a recent `kind='safe_mode_month'` row) rather than as a dedicated `user_subscriptions` table, which adds query weight on the capture-time gate; mitigated by an index on `(user_id, kind, created_at)`.
