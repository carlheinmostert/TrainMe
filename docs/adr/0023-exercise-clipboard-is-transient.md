# Exercise Clipboard is transient by design

The Exercise Clipboard (see `docs/specs/2026-05-25-exercise-clipboard.md`) is in-memory only. Items live in an app-singleton `ChangeNotifier` and clear on cold-start, crash, or process termination. There is no SQLite table, no cloud sync, no per-item management surface inside the paste sheet, and no badge / nudge anywhere outside Studio mode. The only durable artefact a copy produces is the deep-copied row that lands when the user pastes; the clipboard itself is a working-memory buffer with a visible chip while it has contents, and nothing at all when it doesn't.

## Considered Options

We considered **SQLite-backed persistence** (clipboard items survive app restart, surface as a list the user can curate, optionally swipe-to-delete individual items). Rejected because the value compounds with chrome: persistent items invite "what's in here?" questions, which forces a management surface (an empty-state, individual delete, perhaps a search box), which lifts the feature from "transient working memory" into "a half-built second library". The durable library already exists — it's My Workouts, governed by its own scope chip and lifecycle. The clipboard's job is to move things from there (or from any other session) into the session being assembled right now, then get out of the way. We considered **session-scoped persistence** (clipboard contents persist within a single Studio session, vanish on session close). Rejected as an arbitrary boundary: practitioners often gather material from session A and assemble session B, which is exactly the case the boundary breaks. We considered **multi-device cloud sync** (clipboard mirrors via the same `pending_ops` machinery as cached_clients / cached_practices). Rejected as overkill for single-iPhone reality and a permission/consent trap (cross-device sync of in-flight clipboard items means the items are addressable from another logged-in surface, which raises a real privacy question for a feature designed to be ephemeral). The trade-off accepted in choosing transient: a user who crashes the app mid-flow loses the clipboard. This is acceptable because the clipboard holds *pointers* to source exercises (not snapshots — see spec decision D2), which remain on disk and on the cloud regardless; only the in-flight selection is lost, and the user can re-copy in seconds. A future engineer encountering "why doesn't this survive a restart, like every other piece of state in the app?" should land here: the chrome cost of inspection / management was the rejected counter-design, not an oversight.
