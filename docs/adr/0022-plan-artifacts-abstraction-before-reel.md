# `plan_artifacts` table shipped for one kind, designed for many

A new `plan_artifacts` table is introduced with the self-trainer wave (`id`, `plan_id`, `kind`, `status`, `output_url`, `generated_at`, `error_message`, `metadata jsonb`, `UNIQUE (plan_id, kind)`) even though the only `kind` materialised in v1 is `'plan_url'` — the same Plan URL the existing publish flow already produces at `session.homefit.studio/p/{uuid}`. Every Publish writes a row into `plan_artifacts` inside the same transaction as the existing `plan_issuances` audit row; existing plans are backfilled in the migration via `INSERT INTO plan_artifacts (plan_id, kind, status, generated_at) SELECT id, 'plan_url', 'ready', updated_at FROM plans WHERE deleted_at IS NULL`. RLS scopes SELECT through `plans` access (practice members for authenticated, anon via `get_plan_full` which is extended to return an `artifacts` array). The table is RPC-write-only (same lockdown pattern as `credit_ledger`); the only writer is the publish flow. The CHECK constraint on `kind` ("`CHECK (kind IN ('plan_url'))`") is structurally easy to extend (`ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT`); future kinds (`'reel'` for an Instagram-format vertical MP4; `'pdf'` for migrating the on-device PDF handout) become pure schema + renderer additions without forking the publish flow.

## Considered Options

We considered **deferring the table** until the second artifact kind actually ships (today PDF is on-device and Plan URL is implicit in the `plans` row). Rejected because the abstraction needs to exist before the renderer for the second kind is written — otherwise we'd ship the Reel by forking the publish flow, which is the exact divergence the table prevents. We also considered **shipping the Reel artifact in v1** (build the abstraction *with* a real second consumer to validate it). Rejected per Carl's explicit "prepare for it but don't build it now" decision: the Reel rendering pipeline (vertical 9:16 transcode, beat-matched cuts, watermark, social-friendly export) is its own focused engineering wave that would derail the self-trainer wave's shippability. The minimal abstraction lets us land it as one PR; the rendering ships when it's the focused work. We also considered **migrating the on-device PDF handout into the model in this wave**. Rejected — PDF storage opens a real question (which bucket? regenerate-on-demand vs. cache? signed URL lifetime?) that deserves its own wave; the CHECK constraint and `metadata jsonb` accommodate the future migration trivially. The trade-off is that the v1 table has exactly one row-shape (`kind='plan_url', status='ready', output_url=NULL`) which looks under-justified to a reader without context — this ADR is that context. The Plan URL itself remains computed (`session.homefit.studio/p/{id}`), not stored in `output_url`; future kinds with materialised render outputs (Reel MP4 in a new bucket) populate `output_url` with the signed URL.
