# Edit-lock is plan-level, paid-only — free-only plans never lock

The structural-edit lock established by [ADR 0016](0016-fourteen-day-structural-edit-grace.md) — 14 days of free structural editing after first client open, then a padlock that costs one credit to unlock — stays at the **plan level** in the multi-artifact world introduced by [ADR 0022](0022-plan-artifacts-abstraction-before-reel.md): every enabled artifact (Plan URL today, future Reel + Handout + PDF) renders the same shared `exercises` rows, so one set of exercises has one lock. The lock **only arms once a paid artifact is published** for the plan. A plan that has only ever published *free* artifacts — today, just the workout handout at `/h/{uuid}` per [ADR 0027](0027-per-artifact-pricing-with-free-floor.md) — **never locks**, and the practitioner keeps unbounded structural-edit freedom forever. Non-structural edits (reps, sets, hold seconds, notes, filter params) remain free in every state per ADR 0016 unchanged. The 14-day grace window starts on first open of *any* enabled artifact: the existing `plans.first_opened_at` column is redefined accordingly (any artifact's first-open stamp wins; whichever lands first sets the field, subsequent opens don't reset it). On expiry the Studio AppBar surfaces a padlock chip → bottom sheet → "**Spend 1 credit to unlock**" CTA → `unlock_plan_for_edit` SECURITY DEFINER RPC stamps `plans.unlock_credit_prepaid_at`; `consume_credit` reads + clears that stamp on the next publish so there is no double-charge. The CTA verb is **"spend"**, not "buy" — the iOS Reader-App pattern from [ADR 0015](0015-no-iap-paths-ios.md) and [`feedback_ios_reader_app.md`](../../.claude/projects/-Users-chm-dev-TrainMe/memory/feedback_ios_reader_app.md) is unchanged: no prices, no buy buttons, no purchase paths in the mobile app — credits are bought on `manage.homefit.studio` and *spent* in-app. Enforcement lives where it always has: the Flutter Studio UI (`_isPlanLocked` getter and bottom-sheet flow in `app/lib/screens/studio_mode_screen.dart`) plus the atomic `unlock_plan_for_edit` RPC; this ADR adds one server-side predicate ("has any artifact of this plan been published with `paid = true`?") to gate whether the lock arms at all.

## Considered Options

We considered **per-artifact edit-lock** (each enabled artifact has its own lock and its own 14-day grace window — locking the Plan URL while leaving the Reel still editable, or vice versa). Rejected because there is only one set of `exercises` rows shared across all artifacts of a plan — you cannot "lock the handout's exercises but leave the player's editable" because they are literally the same rows in the same table. The artifact system from ADR 0022 gives us many *renderings* of one truth; the edit-lock has to attach to the truth, not to the renderings. Per-artifact locking would either require duplicating exercise rows per artifact (defeating the whole point of the abstraction) or building a complex per-artifact-write-permission layer over the same rows (a UX puzzle with no clean resolution — what does the Studio header even show when three artifacts are in three different lock states?).

We considered **locking free-only plans too** — apply the 14-day grace + padlock regardless of whether any paid artifact exists, so all plans converge on the same lifecycle. Rejected because the lock is fundamentally an **anti-abuse rule on the credit model** ([ADR 0007](0007-credit-billing-model.md)); the original problem it solved was practitioners republishing the same plan URL to ten different clients on one credit. A plan that has only ever been published as a free artifact has no credit at stake — there is nothing to abuse, so there is no policy to enforce. Free-only practitioners (a real segment: people using the platform purely for branded WhatsApp handouts as a top-of-funnel tool) get unbounded structural-edit freedom forever. We accept the trade-off explicitly: a determined practitioner could spam free handouts across many clients with no friction, no rate limit. We bet that the brand-skin upsell plus the funnel value of those handouts make this beneficial rather than abusive. If real-world usage shows abuse, we revisit with a per-practice rate limit rather than reintroducing the lock for free plans.

We considered **starting the clock at first publish instead of first open** (begin the 14-day grace when the practitioner publishes, not when the client opens the link). Rejected for the same reason ADR 0016 rejected it originally: open-triggered timing matches the practitioner / client follow-up cadence — clients return 1-2 weeks later for a follow-up session, the refinement happens *between* open and the next conversation. Publish-triggered timing would expire grace on plans the client never even looked at (the link sits in WhatsApp unread, the practitioner can't edit anymore — bad outcome), and would penalise plans published well in advance of the first session.

We considered **different grace lengths per artifact kind** (e.g. 14 days for the Plan URL, 7 days for the Reel, 30 days for a long-form PDF programme). Rejected — adds complexity for no clear benefit. The 14-day window in ADR 0016 was calibrated to the practitioner / client follow-up cadence; that cadence is the same regardless of which artifact the client opened first, because it is a property of the relationship between practitioner and client, not of the artifact kind.

We considered **no lock, ever** — drop the structural-edit guardrail entirely once we have per-artifact pricing (ADR 0027), on the theory that per-artifact pricing makes the lock redundant because we already charge per publish-event. Rejected because publish is **per-artifact-enablement** (a one-time charge at first mint of each artifact), not per-edit — the same plan URL can be edited and republished indefinitely without re-charging once the artifact exists. The 1-credit-per-paid-plan business rule still needs an anti-abuse rule, which is the lock; without it, the multi-client republish abuse from the ADR 0016 era simply returns. Per-artifact pricing replaces *how* we charge for additional artifacts (Reel costs N credits to enable on top of a Plan URL), not *whether* we cap structural edits on already-paid artifacts.

A few trade-offs are explicit and worth naming. **The lock-arms-on-first-paid-artifact rule** means a plan whose practitioner adds a paid artifact mid-flight (a Plan URL on a previously handout-only plan, say) suddenly becomes lockable from that moment onward. That is intentional — the paid artifact is the abuse surface, and adding it crosses the threshold. **The padlock chip is practitioner-app surface only**; the client never sees lock state, they always see the latest published version of whichever artifact they have the URL to. This stays consistent with publish being one-time-enablement: the lock is a backstage anti-abuse rule, not a user-facing feature. **The redefinition of `plans.first_opened_at`** to "first open of any enabled artifact" is a behaviour change for existing plans where only the Plan URL artifact has ever existed (functionally identical, but the column's *meaning* now spans artifacts) — the migration is a no-op rename of intent; no schema change needed. The Studio padlock-chip triptych mockup at `docs/design/mockups/2026-05-26-studio-status-bits.html` (Section 2) shows the three states the chip can occupy: unarmed (grace active or free-only plan), armed (lock fired), and prepaid (unlock spent, next publish free). Full design context for the multi-artifact world lives in `docs/ARTIFACT_SYSTEM.md`.
