## 27. Per-capture audit log + 24h roster on live view

**Surfaces:** Mobile (write path), live view (`/v/{practice}/{premises}/now`), portal `/audit` follow-up.

**Vision:** Every photo + every video write a row in a new audit table. The live view extends from "currently-recording" to "currently + recently-active in the last 24h" — recently-active sit in a side drawer with their event timeline accessible on tap. The audit log is load-bearing for bystander transparency AND owner-facing investigation.

### Schema (locked)

New table — separate from `audit_events` because volume is 100-1000× higher (per-capture vs per-business-event):

```sql
capture_audit_events (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  practice_id  uuid NOT NULL REFERENCES practices(id),
  premises_id  uuid REFERENCES practice_premises(id),  -- NULL if captured outside any polygon (still logged)
  trainer_id   uuid NOT NULL REFERENCES auth.users(id),
  kind         text NOT NULL CHECK (kind IN ('photo', 'video')),
  started_at   timestamptz NOT NULL,  -- capture time for photo; video-start for video
  ended_at     timestamptz,            -- NULL for photo; video-stop for video
  metadata     jsonb DEFAULT '{}'      -- room for safe_mode_active, exercise_id, etc.
)
```

Indexes: `(practice_id, premises_id, started_at DESC)` for live-view roster query, `(trainer_id, started_at DESC)` for portal per-practitioner drilldown.

Append-only — no UPDATEs (Carl: insert-on-stop for videos). RLS: SELECT scoped via `user_practice_ids()` for the practice owner / member; anon SELECT BLOCKED (live view goes through a SECURITY DEFINER RPC).

### Locked design decisions

1. **Bystander privacy contract — FULL timeline.** Bystander sees photo timestamps and video start+end times. Rationale: enables correlation with venue's own CCTV. If the app log shows nothing but CCTV shows phone-in-hand, that's diagnostic. Public-by-design.
2. **Event kinds — `photo` (one timestamp) + `video` (one row with both start and end).** No separate `video_start` / `video_end` events.
3. **Recently-active scope — premises-scoped.** Per-premises live view shows only events captured AT that premises. Audit log is practice-owned but live-view query filters by `premises_id`.
4. **Side drawer for the stack.** Closed state: small "+N recently active" pill at the left edge. Tap → expands to a vertical avatar list with names. Tap an avatar → popover with their 24h event timeline. Drawer auto-collapses when active session count changes (TBD by executor).
5. **Retention — backlog item.** Will manage later. No retention cron in this PR.
6. **Grace period + animated transition.** When a session ends, the practitioner stays floating on map for ~60s, then fades-and-slides into the drawer stack.
7. **Video audit row — insert-on-stop.** Append-only audit table. Currently-active recording covered by the existing heartbeat + live-map avatar path; the audit row appears in the timeline only when the recording stops.

### Write path (mobile)

- New SECURITY DEFINER RPC `record_capture_event(p_practice_id, p_premises_id, p_kind, p_started_at, p_ended_at, p_metadata)` — practitioner-scoped (caller must be a member of the practice)
- Idempotency: unique constraint on `(trainer_id, kind, started_at)` so retries don't double-log
- Offline-first: queue in existing `pending_ops` table, flush on reconnect
- Photo: insert immediately after capture
- Video: insert when video stop event fires (or when post-capture conversion finishes — pick whichever fires more reliably; recommend stop-event since it's user-action-triggered)

### Live view consumption

New SECURITY DEFINER RPC, anon-callable (same shape as `get_live_sessions`):
`get_premises_active_roster(p_practice_slug, p_premises_slug, p_lookback_hours=24)`

Returns one row per practitioner who has an event in the last N hours at this premises:
```
{
  trainer_id, first_name, last_name, avatar_url,
  currently_active boolean,           -- joined against active_capture_sessions
  last_event_at timestamptz,
  event_count_24h int,
  events jsonb                        -- the timeline: [{kind, started_at, ended_at}, ...]
}
```

Anon access lets the bystander page render without auth. Privacy gate: same `practices.public_profile_listed = true` check as `get_live_sessions`.

### UI shape (live view)

- **Map**: same as today. Floating coral avatar = currently-active.
- **Side drawer trigger**: small left-edge pill `+N` if N>0 recently-active practitioners (not currently active). Coral if any are recently active in the last hour; neutral if older.
- **Drawer expanded**: vertical list of 40px avatar circles + name. Tap an avatar → popover with their 24h timeline (`14:32 photo`, `14:35 → 14:38 video (3 min)`, etc.).
- **Drawer dismissal**: tap outside, Escape key, or tapping the trigger again.
- **Grace period**: when a practitioner's heartbeat goes stale (session ended), they keep their map avatar for ~60s with a slow fade. Then animate slide from map position into the drawer.
- **Newly active**: practitioner appears in drawer (recently-active) → starts recording → fades from drawer + appears on map at their GPS position.

### Owner-facing follow-up (not in scope here)

Portal route `/audit/captures` filtered by practitioner / date / premises / event kind. Useful for investigations. Separate PR.

## 29. Live view — fit-on-load is too loose; polygon reads as tiny

**Surface:** `web-player/live.js` — the auto-fit-on-first-polygon-paint call inside `ensureMap()`'s `mapFittedOnce` guard.

**Issue (Carl's screenshot 2026-05-23):** With a small residential-property polygon, the auto-fit-on-load leaves the polygon at maybe 25% of the visible map area. Lots of unused real estate around it.

**Likely root causes (both stacking):**
1. **Default Leaflet `fitBounds` padding is generous** — typically 20-30px per edge, which is huge proportionally on a small polygon.
2. **Item 24's tactical decision pinned the first-fitBounds `maxZoom` at 19** (the agent kept this cap so the initial view lands on crisp native tiles). Combined with the loose padding, small polygons can't lean in past z19 even though the display cap is z21.

**Direction:**
- Tighten `fitBounds` padding to `[10, 10]` (or even `[8, 8]`) so the polygon takes more of the visible area.
- Raise the first-fit `maxZoom` from 19 → 20. We pay a small upscale-sharpness cost on close-up polygons in exchange for filling the screen.
- DON'T raise to 21 on first-fit — that's the manual-lean-in cap; reserve it for user gesture.
- Re-verify with both Carl's small residential polygon AND a larger gym-sized polygon (the latter shouldn't max out near the cap).

**Files probably involved:**
- `web-player/live.js` — the `fitBounds` call inside `ensureMap()` (search for `mapFittedOnce` and `fitBounds`)
- Mirror sync + sw.js bump

**Dependency:** ships well with item 28 (the manual "fit to polygon" button) — same `fitBounds` call site. Bundle both fits into the same future PR.
