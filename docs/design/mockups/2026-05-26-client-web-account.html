Design notes
01

Spanning identity

The consumer account sits above the practice client-rows. One claim, and every plan from every practitioner the consumer works with shows up in the same list — bridged by the email on file.

The DB-side shape (a client_accounts table, an alias on auth.users, or something else) is open question #1 in docs/ARTIFACT_SYSTEM.md. The consumer's experience, though, is concrete and visible here: one home, three practitioners linked, plans side-by-side regardless of which practice published them.

02

Magic-link only for now

No password. Apple / Google deferred — the magic-link path is enough for the spanning-identity proof. Resend SMTP + Supabase auth already shipped for the practitioner app; the consumer path reuses the same wiring.

The page already knows the plan_id from the URL the consumer arrived on, so claim attaches the current plan to the new account. No silent identity token (rejected — that would tag non-claimers and break the POPIA moat we get from anonymous consumption).

03

Card parity with mobile

Same card pattern as the mobile My Workouts mockup — artifact-kind glyph + title + meta row + a coral-tint provenance banner along the bottom showing the practitioner avatar, name, practice, and a live-link dot.

R-10-style parity. The consumer's "all my plans" surface is one design language across mobile and web. When the mobile card changes, the web card changes in the same PR.
04

Live-linked, not snapshotted

Claiming a plan never freezes it. The consumer always sees the practitioner's latest version — the sage live-dot at the end of the provenance banner is the visible promise.

Pre-claim engagement stays anonymous: analytics events captured before the claim are attributed to the client_sessions row, not to the consumer account. Claim-forward attribution only — see the Analytics section of docs/ARTIFACT_SYSTEM.md.
